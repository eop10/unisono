# 3. Архитектура решения

## 3.1. Что именно надо поддержать

Из требований следуют пять технических ограничений, которые и определяют выбор стека:

1. **Реальное время.** Звук обрабатывается кадрами по 20–25 мс, индикатор обновляется ≥ 30 раз в секунду.
   Алгоритм должен успевать за звуком на среднем телефоне (НФТ-02…НФТ-04).
2. **Низкоуровневый доступ к аудио.** Нужен сырой PCM без агрессивной обработки: AGC, шумоподавление
   и эхоподавление искажают амплитуду и «съедают» затухание струны.
3. **Четыре платформы с разной природой.** Android — ARM и фрагментация; macOS — Apple Silicon/Intel
   и Gatekeeper; Windows — x64 и WebView2; Linux — x86_64, WebKitGTK и ALSA/PipeWire.
4. **Малый объём и офлайн.** Никакого сервера, никакой аналитики, никакой среды выполнения вроде JVM.
5. **Один движок — много инструментов.** Диапазон от B0 (30,9 Гц) до E5 (659 Гц) и выше требует
   адаптивного окна анализа; список инструментов и строёв должен расширяться данными, а не кодом UI.

Отсюда: **ядро на Rust (DSP + аудио + состояние) и тонкий слой представления**.
Выбор Rust закрывает пункты 2 и 4 полностью: нет сборщика мусора, нет виртуальной машины,
задержки и аллокации контролируются явно.

## 3.2. Варианты стека и сравнение

Оценка по шести критериям, вес в скобках. Шкала 1–5, где 5 — лучше.

| Критерий (вес) | Rust + Tauri 2 | Rust-ядро + нативные UI | Rust + Slint | Kotlin Multiplatform |
| --- | --- | --- | --- | --- |
| Одна кодовая база UI (20 %) | 5 | 2 | 4 | 5 |
| Контроль аудио и DSP (25 %) | 5 | 5 | 5 | 3 |
| Качество и «нативность» на macOS (15 %) | 3 | 5 | 4 | 3 |
| Скорость выхода в MVP (20 %) | 4 | 2 | 3 | 5 |
| Размер и зависимости (10 %) | 5 | 4 | 5 | 3 |
| Зрелость экосистемы под задачу (10 %) | 3 | 5 | 2 | 5 |
| **Взвешенный итог** | **4,30** | **3,70** | **3,95** | **4,00** |

**Что важно понимать про «минусы Rust».** Их нет в DSP, аудио и хранении — там Rust строго лучше JVM.
Минус ровно один и он про UI: у Rust нет зрелого нативного UI-тулкита, который одинаково хорошо
работает на Android и macOS. Отсюда три честных пути:

- **Tauri 2** — UI на web-технологиях в системном WebView, Rust-бэкенд. Один UI на обе платформы,
  нативные окно и меню macOS, APK без JVM. Цена — WebView вместо нативных контролов и молодой
  мобильный тулинг.
- **Rust-ядро + SwiftUI/Compose** — лучший вид и поведение, но два UI и +2–3 недели.
- **Slint** — декларативный UI на Rust, нативная отрисовка, но экосистема маленькая и на Android
  всё равно нужен Kotlin-шим Activity.

**Почему не Kotlin Multiplatform (предыдущий вариант).** Модель проще и UI-код один, но JVM даёт
60–80 МБ DMG, GC-паузы в горячем цикле и менее предсказуемый доступ к аудио на desktop.
Rust выигрывает по размеру, задержке и контролю над памятью — при сопоставимой трудоёмкости.

## 3.3. Принятый стек

| Слой | Технология |
| --- | --- |
| Язык ядра | Rust 2021/2024 edition, workspace из четырёх crate'ов |
| UI | Tauri 2 + Svelte 5 + TypeScript + Vite (WebView: WKWebView на macOS, системный Chromium на Android) |
| Мост Rust ↔ UI | Tauri commands (запросы) и `tauri::ipc::Channel<TunerState>` (поток состояний 30–60 Гц) |
| Захват звука | `cpal` на macOS (CoreAudio), Windows (WASAPI) и Linux (ALSA); `oboe` на Android (AAudio/OpenSL ES) |
| Буфер | crate `rtrb` — lock-free SPSC ring buffer, безопасный для real-time потока |
| DSP | чистый Rust, `f32`, без сторонних библиотек; `realfft` — только если понадобится FFT-автокорреляция |
| Хранение | `serde` + `serde_json`, атомарная запись через `std::fs::rename` |
| Логи | `tracing` + `tracing-subscriber` (файл в конфиг-каталоге, без сети) |
| Ошибки | `thiserror` в библиотеках, `anyhow` на границе приложения |
| Тесты | `cargo test`, `hound` для WAV-фикстур, `criterion` для бенчмарков, `proptest` для граничных случаев |
| Сборка | Cargo workspace; desktop — `tauri build`; Android — `tauri android build` (Gradle + NDK) |

Версии крейтов фиксируются в `Cargo.lock` и обновляются отдельной задачей с прогоном тестов
и чек-листа 8.4. `tauri`, `cpal`, `oboe` — три зависимости, от которых зависит поведение на
устройстве; их мажорные обновления проверяются вручную.

### 3.3.1. Платформы и бэкенды

| Платформа | WebView | Захват звука | Упаковка |
| --- | --- | --- | --- |
| macOS 12+ | WKWebView | `cpal` → CoreAudio | per-arch DMG (aarch64, x86_64), ad-hoc подпись |
| Windows 10/11 x64 | WebView2 (Chromium) | `cpal` → WASAPI (shared) | NSIS `.exe` / MSI |
| Linux x86_64 | WebKitGTK 4.1 | `cpal` → ALSA (PipeWire через плагин) | AppImage, `.deb` |
| Android 8+ | системный Chromium | `oboe` → AAudio/OpenSL ES | APK, свой keystore |

UI и ядро общие: `tuner-core` не знает про платформу, `tuner-audio` подставляет нужный бэкенд
через `#[cfg]`, `src-tauri` собирает один и тот же Svelte-бандл. Отличаются только упаковка,
иконки и системные меню.

Границы жёсткие: `tuner-core` не знает ни про аудио, ни про Tauri, ни про файлы;
`tuner-audio` знает только про микрофон и отдаёт `f32`-кадры; `src-tauri` — единственное место,
где сходятся аудио, хранение, состояние и UI.

| Компонент | Ответственность | Не делает |
| --- | --- | --- |
| `AudioSource` (trait) | Открыть микрофон, вернуть фактическую частоту, отдавать `f32`-кадры в канал | Не фильтрует и не анализирует сигнал |
| `CpalSource` / `OboeSource` | Реализация trait под macOS и Android, обработка ошибок устройства | Не знает про ноты и строи |
| `RingBuffer` (`rtrb`) | SPSC-буфер между real-time колбэком и анализатором | Не хранит историю дольше 1 с |
| `LevelGate` | RMS, dBFS, гистерезис тишины | Не решает, что показывать |
| `PitchDetector` | NSDF, выбор пика, интерполяция, `clarity` | Не знает про струны |
| `SmoothingFilter` | Медиана 5 кадров + EMA по `log2(f)` | Не меняет частоту |
| `StringMatcher` | Выбор струны: ручной, авто с гистерезисом, хроматический | Не рисует |
| `TunerEngine` | Оркестрация кадра, состояние `TunerState`, «в строе» | Не знает про UI и IPC |
| `SettingsStore` | `settings.json` и `presets.json`, валидация, миграции | Не хранит аудио |
| `InstrumentRegistry` | Список инструментов и строёв, выбор окна по нижней ноте, правило унисонов | Не знает про UI и звук |
| `bridge` (Tauri) | Команды `get_state`, `set_reference`, `start_listening`; поток `TunerState` в WebView | Не считает центы |
| Svelte UI | Отрисовка, ввод, доступность | Не содержит бизнес-логики |

## 3.6. Поток данных и многопоточность

```text
CoreAudio / AAudio (real-time колбэк, без аллокаций и блокировок)
  └─ rtrb::Producer<f32>  (SPSC, capacity ≈ 1 с)
       └─ std::thread «analyzer» (обычный приоритет)
            ├─ PitchDetector::detect(&window)        ~1–3 мс
            ├─ SmoothingFilter::push(cents)           < 0,1 мс
            └─ watch::Sender<TunerState>  (tokio::sync::watch)
                 └─ Tauri: Channel<TunerState>  (троттлинг 60 Гц)
                      └─ Svelte store → requestAnimationFrame
```

Правила, которые обязательны при реализации:

- **Real-time колбэк ничего не аллоцирует и не блокирует.** Никаких `Vec`, `Mutex`, `println!`,
  `String` в колбэке. Только запись `f32` в `rtrb::Producer` и счётчик переполнений в `AtomicU32`.
  Нарушение даёт щелчки и пропуски звука — это самая частая ошибка в аудио на Rust.
- **Один анализатор.** Кадры обрабатываются строго последовательно; при отставании старые кадры
  перезаписываются (для тюнера важно «сейчас», а не история).
- **Никакого аудио в JS.** В WebView уходят только результаты: `f0`, `cents`, `note`, `clarity`,
  уровень сигнала. Сырой звук через границу IPC не передаётся.
- **Окно живёт отдельно от аудио.** Закрытие/сворачивание окна останавливает захват:
  на Android — по `onPause`, на macOS — по событию окна; Rust получает команду `stop_listening`.
- **Ошибки — значения.** `Result<TunerState, AudioError>` доходит до UI как состояние `Error`,
  а не как паника: `panic = "abort"` в release, паника в аудио-потоке недопустима.

## 3.7. Бюджеты производительности

| Операция | Бюджет | Как проверяем |
| --- | --- | --- |
| `PitchDetector::detect`, окно 4096, 48 кГц | ≤ 3 мс (Snapdragon 6xx, Cortex-A78) | `criterion` на arm64 + замер на устройстве |
| То же, окно 8192 | ≤ 6 мс | `criterion`, отдельный бенч |
| То же, окно 16384 | ≤ 14 мс | `criterion`, отдельный бенч; проверка на бас-гитаре |
| Полный кадр конвейера | ≤ 5 мс | `tracing`-спан в debug, p95 в логе |
| Отрисовка в WebView | ≤ 4 мс, 60 fps | Chrome DevTools, профиль на 10 с |
| Память под DSP | ≤ 1 МБ (4 окна + рабочие буферы) | `dhat` в тестах |
| Задержка «звук → экран» | ≤ 120 мс | генератор щелчков + видеозапись 240 к/с |
| Размер release-бинарника | ≤ 9 МБ (strip + LTO) | `cargo bloat`, CI |

NSDF «в лоб» — около 2,4 млн умножений-сложений на кадр (4.5). На Rust это 1,5–3 мс без ручного
SIMD за счёт автовекторизации; узкое место, если оно появится, — не язык, а сам алгоритм
(переход на FFT-автокорреляцию). Менять алгоритм «на глаз» без замеров запрещено.

## 3.8. Границы и точки расширения

- **Новые инструменты.** Добавляются записью в `music/instruments.rs` и `music/tunings.rs`;
  UI и DSP не меняются, если нижняя нота не уходит ниже 30 Гц.
- **iOS.** Tauri 2 поддерживает iOS, `tuner-core` от платформы не зависит; нужен `CoreAudioSource`
  на `cpal`/`objc2` и тот же UI. Отдельный crate, переписывать логику не нужно (**⚠️ Q8**).
- **Бас-гитара.** Окна 8192–16384 и `τ_max` до 1600 — параметры `DetectorConfig`, UI не меняется (4.2.3).
- **Стробоскоп.** Фаза накапливается как `∫(f − f_цел) dt` из той же оценки частоты: добавляется
  только Svelte-компонент, DSP не трогается.
- **Нативный UI (план Б).** Если WebView не устроит по виду или задержке: `tuner-core` и
  `tuner-audio` остаются, `src-tauri` заменяется на SwiftUI-оболочку (FFI через `uniffi`)
  и Kotlin/Compose-оболочку (JNI). Это и есть вариант «Rust-ядро + нативные UI» из 3.2.
- **Калибровка под микрофон.** Таблица поправок по частоте (компенсация АЧХ) — в MVP не нужна,
  так как измеряется частота, а не амплитуда.
